These rules apply to EVERY task. If a prompt conflicts with this file, stop and ask; do not guess.

## 1. What this is

A single-user, local-first Deadline Manager. Users create deadlines, see urgency via configurable red/yellow/green thresholds, and move items to history ONLY by explicit completion. Overdue != completed.
OUT OF SCOPE (do not build): authentication, multi-user, reminders, recurring deadlines, dark mode, search, full editing of existing deadlines, drag-and-drop.
There is no auth, so this is a localhost app. Never describe it as production-ready.

## 2. Stack (no substitutions)

- Frontend: ALREADY EXISTS in `frontend/` (generated by Lovable: React + TypeScript + Vite + Tailwind + shadcn/ui). Treat it as existing code. Do NOT redesign or restyle it. Only: integrate with the real API, fix real bugs, add tests.
- Backend: Java 21, Spring Boot 3.x, Maven, Spring Web, Spring Data JPA, Bean Validation, Flyway. NO Node/Python backend. NO Lombok.

## 4. Locked product decisions

1. Required: title (1–150) and due date/time. Short description optional (≤200). Long description optional (≤5000).
2. Create: due date must be in the future (server enforces). Change Deadline: past dates allowed.
3. Completion = circular check button on each card. The card's three-dot menu has EXACTLY: Delete, Change Deadline.
4. Card click opens a read-only detail dialog (the only place the long description is shown).
5. Overdue shows red with "Overdue by …" text; never a positive countdown.
6. History sorted by completedAt DESC; each item has Restore and Delete (with confirmation).
7. Sidebar toggle = horizontal three-dot icon; card menu = vertical three-dot icon.
8. Sidebar has exactly three sections: List Deadlines, Deadline Settings, Previous Deadlines.
9. No fake data anywhere in the final product. Empty states are real empty states.

## 5. Urgency logic (single source of truth; implemented in the frontend)

Thresholds are TOTAL HOURS: `redThresholdHours` (default 24), `yellowThresholdHours` (default 72).

```
remaining <= 0                 -> OVERDUE (red)
remaining <= redThresholdHours -> RED
remaining <= yellowThresholdHours -> YELLOW
otherwise                      -> GREEN
```

Colour is derived at render time. NEVER stored in the DB or on deadline objects. Validation (frontend AND backend, same rules): integers, `0 < red < yellow <= 8760`.

## 6. Time zones

- Wire format: ISO-8601 UTC strings. Backend uses `java.time.Instant` only. Jackson `write-dates-as-timestamps: false`. `hibernate.jdbc.time_zone=UTC`. DB: `timestamptz` only.
- Frontend converts picker values with `new Date(local).toISOString()` and displays in the browser's local zone. Countdown math uses absolute milliseconds.

## 7. Schema rules (Flyway only)

- `spring.jpa.hibernate.ddl-auto=validate`. Never `update`/`create`. Never edit an applied migration; add `V2__…`.
- `deadlines`: id BIGINT identity PK, title, short_description, long_description, due_at, completed bool, created_at, updated_at, completed_at (nullable). CHECK: completed ⇔ completed_at IS NOT NULL. Indexes on (completed, due_at) and (completed, completed_at DESC).
- `app_settings`: single row, id SMALLINT PK CHECK (id = 1), red_threshold_hours, yellow_threshold_hours, CHECK (red > 0 AND yellow > red), updated_at. V1 inserts defaults (24, 72).
- SUPABASE EXPOSURE FIX (mandatory, in V1): `ALTER TABLE … ENABLE ROW LEVEL SECURITY` on BOTH tables with NO policies, and revoke all privileges on both tables from the `anon` and `authenticated` roles, inside a `DO` block that first checks the roles exist in `pg_roles` (so the migration also works on plain Postgres). Purpose: Supabase auto-exposes tables through its Data API; only the backend may touch this data.

## 8. REST contract (do not rename)

| Method | Path                                        | Success        |
| ------ | ------------------------------------------- | -------------- |
| GET    | /api/deadlines/active (dueAt ASC)           | 200            |
| GET    | /api/deadlines/completed (completedAt DESC) | 200            |
| GET    | /api/deadlines/{id}                         | 200            |
| POST   | /api/deadlines                              | 201 + Location |
| PATCH  | /api/deadlines/{id}/due-date                | 200            |
| POST   | /api/deadlines/{id}/complete                | 200            |
| POST   | /api/deadlines/{id}/restore                 | 200            |
| DELETE | /api/deadlines/{id}                         | 204            |
| GET    | /api/settings                               | 200            |
| PUT    | /api/settings                               | 200            |

Errors: 400 validation (with `fieldErrors`), 404, 409 (complete an already-completed item; restore an active item), 500 generic. Body: `{ "timestamp", "status", "error", "message", "fieldErrors": { "field": "msg" } }`. No stack traces or SQL in responses.
JSON shapes: Deadline `{id, title, shortDescription, longDescription, dueAt, completed, createdAt, completedAt}`; Settings `{redThresholdHours, yellowThresholdHours}`.

## 9. Security & config

- No real secrets in source or git. Config comes from `backend/.env` (gitignored), loaded via `spring.config.import=optional:file:.env[.properties]` (the working directory must be `backend/`); OS env vars override it. Keys: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `CORS_ALLOWED_ORIGINS`, `SERVER_PORT` (default 8081). `DB_PASSWORD` has NO default. Fail fast with a clear message if required keys are missing.
- NEVER ask the user to paste credentials into chat. NEVER print, log, or commit `.env` contents. The user fills `backend/.env` themselves.
- Supabase connection: use the SESSION pooler or direct connection string from the Supabase dashboard (Connect panel), with `?sslmode=require`. Do NOT use the transaction pooler (port 6543): it breaks Flyway locking/prepared statements. Hikari `maximum-pool-size: 5`.
- CORS: origins from `CORS_ALLOWED_ORIGINS` (comma-separated; must include the real frontend dev origin(s) for both `localhost` and `127.0.0.1`). Methods GET, POST, PUT, PATCH, DELETE, OPTIONS; header Content-Type. No `*`.
- `spring.jpa.open-in-view=false`. Controllers return DTO records, never entities. Business rules live in the service layer.
- Frontend: never `dangerouslySetInnerHTML`; user text rendered as plain text only.
